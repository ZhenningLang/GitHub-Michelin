# object-storage

> 分类节点。你自建的 S3 兼容对象存储服务端——承载备份、日志归档与应用对象的那一层。

## 本分类项目

| 项目 | 何时用 | 健康度 | 页面 |
| --- | --- | --- | --- |
| **Silo** | 你已经在跑 MinIO、而上游社区版已经终结时用它——Silo 让 S3 API、落盘格式与 `MINIO_*` 命名继续可用；代价是可执行文件／软件包／镜像改名为 `silo`，且它是单一维护者对单一代码库的 fork。 | C（5/6） | [→](silo.zh.md) |
| **MinIO** | 用这一页决定你手上已经跑着的 MinIO 怎么办：社区仓库已归档（2026-04）且无人维护，所以这是“迁到在维护的 fork 或别的存储”的选择，而不是新部署的选项。 | C（6/6） | [→](minio.zh.md) |
| **Garage** | 想用几台分散各地、便宜的机器拼出一个 S3 端点、跨站点复制、其中一台离线仍可用时用它——但它的 S3 能力面刻意不完整（没有 ACL／策略语义）。 | B（4/6） | [→](garage.zh.md) |
| **SeaweedFS** | 真正的约束是对象数量——十亿级小文件——且你想要一个 `weed` 二进制同时提供 S3、文件系统与表层、靠加卷服务扩容量时用它。 | B（6/6） | [→](seaweedfs.zh.md) |
| **Ceph** | 你需要基金会治理的同一平台提供对象、块与文件、且养得起一个真正的存储集群时用它——只需要一个 S3 桶时属于过量的工具。 | A（4/6） | [→](ceph.zh.md) |

## 对比矩阵

| 选项 | 是否收录 | 健康度 | 一句话取舍 |
| --- | --- | --- | --- |
| [Silo](silo.zh.md) | ✅ | C（5/6） | MinIO 的代码库加上一条在维护的发版线，且不用迁数据——代价是单组织背书、AGPL 义务，以及一条“条件式”而非无痛的升级路径。 |
| [MinIO](minio.zh.md) | ✅ | C（6/6） | 一代人标准化的 S3 服务端，现已归档、无人维护——它的格式与 API 由 Silo 延续，所以只有在复现某个冻结构建时才选它。 |
| [Garage](garage.zh.md) | ✅ | B（4/6） | 用不可靠、异构的机器拼出多站点 S3，单个 Rust 二进制——不是 MinIO 的即插即用替代，也不是完整的 S3 功能面。 |
| [SeaweedFS](seaweedfs.zh.md) | ✅ | B（6/6） | 一个二进制、每 blob 一次读盘、靠加卷服务扩容量，另有文件系统与湖仓这一面——架构不同，活动部件也比单台 S3 服务端多。 |
| [Ceph](ceph.zh.md) | ✅ | A（4/6） | 非营利基金会治理、集群规模的对象＋块＋文件——本分类里最重的运维账单，也超出大多数纯 S3 需求所需。 |

## 什么该放这里

你自己运维的对象存储：S3 兼容服务端（随着分类成长，也包括架在其他后端之前的 S3 网关）及其客户端与配套组件。当前这一组按设计中心分：MinIO／Silo 是一台 S3 服务端加 MinIO 格式兼容，Garage 面向跨站点的廉价机器集群，SeaweedFS 面向极大对象数量加一个文件系统面，Ceph 是同时提供块与文件、受基金会治理的平台。不含只做块／文件的存储平台，不含写入对象存储的备份软件，也不含托管的对象存储服务。
