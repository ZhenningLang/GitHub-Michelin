先看结论

这批项目解决三类问题：让 agent 操作工具、把资料变成可用内容，以及替换现有基础组件。 不要把“技能指令”“真实工具权限”“完整应用”混为一谈。前者教模型怎么做，后两者才实际接触编辑器、桌面、数据库或账号。

新增项目：什么时候选，什么时候避开

项目真正解决的问题决定性取舍与边界
LCU现有编程 agent 卡在原生应用弹窗，无法完成导出等操作。复用已装 ChatGPT 应用的电脑控制引擎，不必更换 agent；但依赖闭源运行时，Linux 没有逐应用授权，也不自带虚拟机。
ZCode希望桌面、网页和 CLI 使用同一套 agent 与任务工作流。它提供自己的运行时，不只是包一层现有 CLI；默认没有操作系统沙箱，开放构建的原生 Computer Use 不可用。
FounderOS一个人经营业务，要在收件箱、收入和 agent 工作之间来回查。它是可修改的业务监管界面，不是安装即运行的自治公司。真实 agent 看板依赖另设的 Paperclip；演示数据和已配置徽标不证明真实业务已接通。
Nezha多个 Claude Code／Codex 任务看起来都安静，需要找出待审批和待验收的那个。本地桌面工作台集成终端、会话、文件与 Git；默认是本地目录，工作树须主动选。启动会改 Codex 全局 hook，部分启动参数绕过审批或信任，不能把工作台当沙箱。
leanrea只想解释成品应用的一项功能，agent 却反复挑工具和读整包脚本。短指令减少接线成本，但不提供分析引擎或证据账本。当前有危险清理、转义管道和缺失脚本，只适合授权范围内、有人监督的调查。
SAG相似段落检索答不出跨文档的事件与实体关系。提供个人资料库、关联检索和引用读取；默认快速策略不走完整扩展路径，默认名字登录与全库 MCP 也不是租户隔离。
EmDashAstro 网站编辑改一个标题也要提 PR 和重建。在 Astro 内加编辑后台与数据库，不是兼容 PHP 插件的 WordPress 替代安装包。插件沙箱按平台不同，原生插件不受其隔离。
OXR多栏 PDF 的文字、公式和表格解析混在一起，想独立替换区域检测器。专门的 PDF／图片 GPU 服务，不是通用格式转换。源码可见许可含规模与托管竞争限制；占位 key 不等于鉴权，内存任务也不适合直接当持久批处理队列。
Biscotti想在 Mac 本地保存会议、分辨说话人并生成会后摘要。不需要云推理账号，但限 Apple Silicon、macOS 15 及以上；不是会中行动 agent。PolyForm Perimeter 禁止竞争用途，MCP 开启后本机程序可读会议。
twitter-cli想把自己的 X 书签和信息流接给终端脚本。无需另建开发者应用，但把会话 cookie 交给非官方 HTTP 客户端。搜索修复尚未合并，鉴权失败还能回读其他浏览器，不宜作为稳定业务数据源。
md2wechatMarkdown 成稿还要补封面、检查图片与元数据，再创建公众号草稿。完整 Go CLI 加操作规程，不只是技能文本。主排版路径依赖付费服务并外发文章；公司营收相关工作与客户交付受许可限制，AI 模式只返回待执行提示词。其他平台仍由宿主浏览器完成。
gzh-design-skill已有文章要按主题组件排成公众号样式，再手动复制到编辑器。六套主题与静态检查，不是确定性排版器，也没有自动发布。正文保真和手机／暗色显示仍需验收；有些检查只警告、退出仍为零。许可按 AGPL 原文，不按 README 的泛化禁收费说法。
KiviDBRedis 风格业务还需要同库关键词与向量检索。内置搜索与多核实现减少一份存储，但 AGPL、短公开历史及兼容／恢复边界需要验证。当前只有每秒刷盘，确认写入不等于同步落盘。
microG不带 Google 套件的安卓系统仍要运行已有应用。替换设备上的服务实现，不替换 Google 后端。通常需要系统支持签名伪装；银行、完整性检查和推送兼容性要逐应用验收。
GameDev Agent Skills通用 agent 混用引擎版本，缺跳跃、存档和发布的领域知识。它是按引擎与版本选取的技能目录，不是编辑器连接。文字路由不能证明游戏能运行，仍需引擎编译和场景测试。
Unity-MCPagent 写完 Unity 脚本，还要人手动挂组件、抄控制台错误。真正连接编辑器并可执行 C#，不是仅给开发建议；权限面更大，也不是沙箱。根 Apache 许可不覆盖 Code-Exec 的 PolyForm Shield 例外。
紫微斗数需要研究传统排盘约定与文化娱乐界面，而不是重写整套排盘规则。可复用引擎与演示，不含完整商业站后端和解读生成器。时间边界、流派默认与引文权利需核对；排盘一致不证明预测有效。

横向对比选题池

以下分类连同子分类，当前均已有至少四个项目。问题是后续写作选题，不是本批追加开发任务。

  • 桌面自动化： 复用已装闭源引擎、调用独立桌面驱动，还是先买一层可丢弃虚拟机隔离？
  • 数据库引擎： 内置关键词／向量搜索省掉第二份数据，是否值得承担兼容、许可和恢复语义的迁移成本？
  • agent 监管界面： 你缺的是待人处理队列、远程会话入口，还是自动回送 PR／CI 反馈的控制平面？
  • 工程技能： 如何把通用开发流程、领域知识和实际执行工具分开，避免“装得多”反而增加指令冲突？
  • 结构化检索： 长文档章节树、跨文档事件关联和持久知识图谱，分别在哪类问题上值得额外建索引？
  • 终端编码助手： 自带运行时、模型厂商第一方助手和现有 CLI 的监督层，究竟在哪一层替换最省迁移成本？
  • UI 品味技能： 没有品牌规范时怎样形成设计方向，有了设计系统以后又该删掉哪些“品味推断”？
  • 游戏开发： 选轻量引擎做完整小项目，还是连接 Unity 编辑器让 agent 直接改场景，验收责任如何划分？
  • 社媒管理： 官方 API、浏览器桥和会话 cookie 客户端，在权限范围、账号风险和可恢复发布上如何取舍？
  • 文档解析： 选混合格式／CPU 管线，还是拆开版面检测与识别的 GPU 服务，商用许可和长任务恢复要付出什么？
  • 内容生产技能： 主题组件装配、文章创作和账号草稿工具各负责到哪一步，怎样防止“本地检查通过”冒充“正文保真且已发布”？

Inner-loop evidence：结构门禁、范围质量扫描与工具测试。 Acceptance evidence：真实 Chrome 标签逐项提交后关闭；页面、生成图、双语入口与反向索引接通，最后重扫无新增候选。最终机器对账结果见本批验证文件。 Holdout / unseen evidence：不适用模型效果实验，以源码限制、未合并修复和真实标签作为边界抽样。 Holdout 来源类别：真实捕获及源码抽样。 预期值来源：用户需求与 tools/schema.md 外部契约。 本次改动相对冻结点的位置：只改内容生成侧，未改工具、判定器、门禁阈值或个人 harness。
